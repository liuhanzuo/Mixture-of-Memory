## 3. VERDICT on the NFE seam: **STILL OPEN, but narrowed — and one claim must be rewritten**

### 3.1 What SEAM B currently asserts

> "Every variable-length paper reports token-ratio efficiency; none reports NFE for its own
> loop." … "**A method that 'matches the best tuned fixed-length baseline' while spending more
> forward passes than that baseline has not made decoding better; it has made tuning
> unnecessary.**"

### 3.2 Verbatim evidence — the metric names each candidate actually reports

Read from the Anthology camera-ready PDFs. `\bNFEs?\b` **case-sensitive** count is 0 in every
one; earlier case-insensitive greps that appeared to hit "NFE" were matching
*i**nfe**rence* / *co**nfe**rence* / author names (*Jia**nfe**i*, *Li**nfe**ng*) — I enumerated
every `\w*nfe\w*` token to confirm.

**① Saber (`2026.acl-long.165`) — THE ONE THAT MATTERS.** Verbatim, Appendix J:

> "In addition to performance, we also measure the **Step (i.e., average generation steps per
> sample)** and **Time (i.e., total generation time)**."
> "In the fixed-length decoding scenario, we set the **generation length to 256 tokens**."
> "we report the average results of **five trials**"

Its Table 1 gives `Pass@1 / ET / Step / Time` **per method**, e.g. on HumanEval:

| Method | Pass@1 | Step ↓ | Time ↓ |
|---|---|---|---|
| Confidence (standard) | 43.29 | 256 | 2:11:52 |
| Fast-dLLM | 39.63 | 256 | 59:40 |
| Fast-dLLM (+parallel) | 39.63 | **96.24** | 25:25 |
| WINO | 40.24 | **100.12** | 57:10 |
| **Saber** | **45.12** | **118.92** | 41:55 |

This is a **fractional realized step count and an absolute wall-clock, for its own adaptive
loop, against baselines at a pinned canvas of 256.** It is exactly the accounting SEAM B says
is absent. Note it even shows Saber spending *more* steps than Fast-dLLM(+parallel)
(118.92 vs 96.24) while scoring higher — the cost–quality trade stated honestly, not hidden.

**② SchED (`2026.findings-acl.1782`)** — partial, and it *defines away* the total:

> "Reporting quality and speedup separately can obscure Pareto differences between methods.
> To jointly capture both aspects, we define the **Quality-Penalized Speed (QPS)** metric:
> QPS_γ = **speedup** × (score / baseline score)^γ"

`speedup` itself is **never defined by an equation anywhere in the paper** (I searched for
`speedup is/defined/=/ratio of`; no definition found). Total steps and wall-clock appear
**only in Appendix D**, explicitly framed as qualitative:

> "**D Qualitative Assessment of SchED** … we present **representative per-instance examples** …
> Table 9 reports the **realized number of denoising steps and wall-clock latency** under
> identical inference settings"

So: per-instance realized steps + seconds exist (Table 9: e.g. base 128 steps / 15.586 s →
SchED 8.006 s), but the aggregate claim ("≈4× on instruction-tuned") rests on an undefined
`speedup`. Compute is reported only as a lump: "8×AMD MI210, with a total compute allocation
of **52 GPU-days**". **Canvas is pinned and tabulated** (Table 4: GPQA 128, GSM8K 256, WMT
256, MultiNews 512, HotpotQA 32) — good on (c).

**③ Focus-dLLM (`2026.acl-long.556`)** — reports **Throughput (tokens/s)** and TPS
("29.6×" red speedup annotations vs Vanilla at 32K; Table 5 has a `Throughput(16K)` column).
No steps, no NFE, **`latency` and `wall` appear 0 times**, `FLOP` 0 times. And it is
**attention sparsification** — it does not change the number of denoising iterations, so a
throughput metric is legitimate for it and it is **not** an adaptive-length method. It does
not touch the seam.

**④ Ada-DLM (`2026.acl-long.819`)** — **Token-Per-Second (TPS)** end-to-end plus
per-task `Speedup` ratios (Fig. 5, Table with `Speed (TPS)` column: Dream-7B Vanilla 14.7 →
Ours 97.7). Also reports absolute seconds-per-sample ("Vanilla ≈341s → Ada-DLM ≈8.26s") and
profiling overhead "< 0.2%". No step counts, no NFE. This is a *token*-normalised metric —
the same normalisation SEAM B objects to in LR-DLLM — but Ada-DLM prunes computation without
changing output length, so the denominator is stable and the objection does not bite.

**⑤ Parallelism and Generation Order (`2026.findings-acl.357`) — NOW READ IN FULL, gap closed.**
The Anthology PDF is **25,951,797 bytes** and every plain fetch truncated it (root cause in §6 —
it was never a broken server). Resolved by reading the **arXiv version `2601.15593`**
(6,682,219 B, valid `%%EOF`, 41 pages, title matches the Anthology title verbatim), located via
a DBLP query that also surfaced a **5th dual-record** (`ACL 2026` + `CoRR 2026`).
`\bNFEs?\b` = 0; `generation length` = 0; `number of steps` = 0; `total steps` = 0; `FLOP` = 0.

Its metrics are defined, verbatim:

> "We report the Accuracy (ACC), **Average Finalization Parallelism (AFP)—a hardware-agnostic
> speed metric**—and Tokens Per Second (TPS)."

AFP is a **per-step parallelism** measure (tokens finalized per decoding stage; Fig. 3:
1.95–6.20 on normal samples, 18.32–26.11 on repetitive ones), paired with a runtime model in
which *"Let `T_step(m)` be the **wall-clock time of one stage (one forward pass for that
stage)**"* and `L/m` is the "effective parallelism level". So the reported quantity is
**tokens-per-stage — a per-token/per-step normalisation, not a total.** TPS appears only
sparsely (Table 10 is `–` for most columns).

**Verdict on ⑤: does NOT preempt.** It is the nearest thing to total-cost accounting in the ACL
set — `m`, the number of sequential stages, is one factor of total NFE — but it never reports
the total, never pins or sweeps a generation-length budget, and it is a *measurement* paper
about parallelism and ordering, not an adaptive-length method. **P2 should cite it and either
adopt AFP or state why not**, since it is now the published metric in this space.

**⑥ ⚠️ `arXiv:2510.18480` — "How Efficient Are Diffusion Language Models? A Critical
Examination of Efficiency Evaluation Practices"** (Peng, Liu, Dong, Cheng, Li, Tang, Wang,
Zhao — RUC/UIBE/Tsinghua/CityU). **Not an ACL paper**; venue **`CoRR 2025`
(DBLP, sole record) / OpenReview `venueid: OpenReview.net/Public_Article` showing
`venue: CoRR 2025`** — i.e. **NOT-FOUND at a conference, not proven-preprint**, per the
standing rule. Recovered from the log's own shortlist (`### 2510.18480 How Efficient Are
Diffusion Language Models`), **absent from the Claude report.** `\bNFEs?\b` = 0, but it is
*about* the accounting problem. Verbatim §3:

> "**Efficiency Metrics.** Efficiency reporting are inconsistent across studies, making it
> difficult to compare models fairly. Some studies report latency per token, while others
> focus on throughput (tokens per second) on specific hardware setups. These metrics, while
> useful, **often fail to capture the complete picture. For example, a model might show high
> throughput, but if each step involves heavy computation, the overall cost could still be
> high.** … it would be helpful to include standardized metrics that consider both
> computational cost and decoding performance. Examples might include **FLOPs per token or
> throughput under fixed resource constraints**."

and its three named issues: **Evaluation Scope** ("fixed generation length" → unrepresentative),
**Infrastructure Implementation** ("mixing algorithmic innovations with kernel- or system-level
optimizations, which blurs the boundary between algorithmic and engineering gains"),
**Efficiency Metrics** (above). It also pins the canvas rigorously — sweeping generation
lengths **64/128/256/512/1024/2048** × batch size × 0-/5-shot, and forcing AR to keep
generating past `<eos>` to the target length "to ensure a fair comparison of throughput".

**Why it does NOT preempt our seam**: its question is *DLM vs AR throughput*, not
*adaptive-length methods vs their own baseline*. Its remedy is FLOPs/token and
throughput-under-fixed-resources — **both per-token normalisations**, i.e. the very thing
SEAM B argues breaks when the method changes the token count. And it explicitly files
adaptive length under **future work**:

> "**Variable-Length Generation in DLMs.** Existing DLMs often adopt a predefined generation
> length, which often leads to redundant computation or suboptimal generation quality. …
> Therefore, a more principled approach is to enable DLMs to **adaptively control their
> generation length** according to the difficulty of each sample, which represents an
> **important direction for future research**."

**So the strongest "efficiency evaluation is broken" paper in this field explicitly leaves
adaptive-length accounting open, and even names it as the next step.** That is close to an
invitation, and it is the single best citation for why the seam is worth a paper. It also
raises the bar: our accounting must not be *only* per-token, or we reproduce the flaw
2510.18480 diagnoses.

### 3.3 Adjudication

| SEAM B sub-claim | status after this harvest |
|---|---|
| "no *variable-length* paper reports total NFE for its own loop" | **HOLDS.** None of the 17 ACL-2026 papers is an adaptive-*length* method. The canvas-changing family (DAEDAL, CAL, LR-DLLM, ρ-EOS, DreamOn) is entirely outside ACL 2026. |
| "nobody in the dLLM efficiency literature reports honest total step + wall-clock for their own adaptive loop" | **FALSIFIED by Saber.** `Step` + `Time` per method, canvas pinned at 256, 5 trials. Must be cited and conceded. |
| "the literature conflates 'better decoding' with 'tuning made unnecessary'" | **HOLDS, and is strengthened.** Saber shows the honest version is publishable at ACL Long — which makes its absence in the length papers a *choice*, not a norm. |
| "per-token normalisation hides that adaptive methods change the denominator" | **HOLDS and sharpens.** Ada-DLM/Focus-dLLM legitimately use TPS *because* their output length is fixed. That is precisely why TPS is illegitimate for a length-changing method. Saber shows what to report instead. **And 2510.18480 — the field's own critique paper — proposes FLOPs/token and throughput-under-fixed-resources as the fix, both per-token. So the flaw survives even in the paper written to fix evaluation.** |

**⚠️ Additional requirement created by 2510.18480**: it shows dLLM acceleration gains
"mainly offer gains at small batch sizes, with their benefits diminishing upon scaling"
(abstract) — so **any wall-clock/throughput number we report must state its batch size**, or
a reviewer holding that paper will discount it. Its own protocol (gen length ∈
{64,…,2048} × batch size × 0-/5-shot, AR forced past `<eos>`) is the standard to match or
explicitly depart from.

### 3.4 Verdict

**VERDICT: the NFE seam is STILL OPEN. Do not cancel GPU work on it.** But the framing must
change from *"nobody reports it"* to:

> **"Total-step + wall-clock accounting at a pinned canvas is established practice in the
> adaptive-*step* literature (Saber, ACL 2026 Long, reports `Step` and `Time` per method at
> `gen_length=256`). It is absent from the adaptive-*length* literature, where it matters
> more — because changing the canvas changes the denominator of every per-token metric.
> We supply it."**

That is a stronger paper than the original: it has a positive exemplar to point at instead of
an unfalsifiable absence claim, and it removes the reviewer's easiest objection ("Saber does
this, your related work is incomplete").

**Concurrency note**: Saber's arXiv preprint is `2510.18165` (Oct 2025) and SchED's is
`2512.02892` (Dec 2025) — both >3 months before 2026-08-15, so **neither is "concurrent"**.
They are prior work and must be cited. Neither *preempts*, because neither varies the canvas.

### Root cause of the "truncated PDF" failures — I misdiagnosed it, then fixed it

I recorded `2026.findings-acl.357` as an unrecoverable server-side truncation after 6 failed
fetches (819,200 → 2,899,968 → 6,717,440 → 17,137,664 B, never any `%%EOF`). **That diagnosis
was wrong.** A `HEAD` request shows `Content-Length: 25951797` with `Accept-Ranges: bytes` —
**the file is simply 26 MB and each of my `-m` timeouts was cutting it off mid-stream.** The
tell was there and I ignored it: the size *grew monotonically with every longer timeout*, which
is the signature of a slow-but-healthy transfer, not a broken endpoint.

Two further lessons from the fix:
- **`curl -C -` made it worse, silently.** Resuming onto an already-truncated file produced
  **27,360,821 bytes — larger than the true 25,951,797** — i.e. a corrupt file that would have
  passed a naive "is it big enough?" check. Byte-count alone is not an integrity test; only
  `Content-Length` equality plus `%%EOF` is.
- **Always `HEAD` for `Content-Length` before concluding a download is broken**, and prefer the
  arXiv mirror for large Anthology PDFs (6.7 MB vs 26 MB here for the same paper).

### Tooling failures worth recording (both would have produced false negatives)

1. **Env-var proxy is silently ignored by curl here.** `export http_proxy=…https_proxy=…` →
   `HTTP:000`, no `-o` file written, curl trying to reach `199.232.167.42:443` directly.
   **Only explicit `-x http://hy-proxy.woa.com:3128` works** (→ HTTP 200, 3,102 B, title
   "Large Language Diffusion Models"). Every fetch in this document used `-x`.
2. **⚠️ The shell's `grep` is a `ugrep` wrapper with `-I` (skip-binary) and `--ignore-files`.**
   pymupdf-extracted text is classified `data` by `file`, so **`grep` returned ZERO matches on
   it — silently.** My first pass therefore "found" 0 hits for `diffusion` in a paper titled
   *…Diffusion Language Models*; `/usr/bin/grep` gives 76. Caught by positive control.
   **All text analysis in §3 used `/usr/bin/grep` or Python `re`.** Any agent grepping
   extracted PDF text with the wrapped `grep` will get false negatives. (Log-ID extraction was
   re-run under both and matched exactly: 406/33/34.)
