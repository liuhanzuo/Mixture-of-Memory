# QCMem 方法说明（给 collaborator 的入门版）

> 目的：让没接触过这个项目的合作者，读完这一份就能理解 QCMem 是什么、为什么这么设计、和你可能熟悉的方法（RAG / KV cache / MemoryLLM）什么关系。不需要先读代码或论文 draft。
> 配套：正式结果见 `status/QCMEM_PAPER_DRAFT.md`；本文只讲逻辑与直觉。

---

## 0. 一句话

**QCMem = 把长文档切块，每块只跑过模型的前半段、缓存"半成品"隐藏态；回答问题时用检索挑出相关的几块，拼起来只跑模型的后半段得到答案。** 好处是：喂给模型的东西长度恒定（跟原文多长无关），所以在超长上下文（128k+）上，别的方法都因为超出模型窗口崩掉时，它还能用。

---

## 1. 要解决的问题

一个 8B LLM（比如 Qwen3-8B）原生只能处理 ~128k token 的上下文。给它更长的文档，有几条常见路子，各有痛点：

| 做法 | 痛点 |
|---|---|
| **直接全喂（full-context）** | 超过窗口（128k）直接崩；显存 O(L²)，长了就 OOM |
| **RAG（检索片段再拼）** | 检索的是原始文本，要重新跑整个模型，算力没省 |
| **KV cache 复用 / 压缩** | 存的是全部 token 的 KV，内存随长度线性涨；超窗口仍崩 |
| **压缩式 memory（如 MemoryLLM）** | 固定大小 memory bank 会溢出，早期信息被挤掉（FIFO 丢失）|

**我们想要的**：一种"喂给模型的东西长度恒定、显存恒定、且不受原生窗口限制"的长上下文记忆机制。

---

## 2. 核心观察（为什么能这么做）

Transformer 有 L 层（Qwen3-8B 有 36 层）。我们发现一个可利用的**分工现象**：

> **前面一部分层主要在"理解"（把 token 变成语义表示），顶部少数层主要在"生成"（把语义转成下一个词的概率）。**

（这个我们用 probing + 截断下游任务验证过，跨 Qwen/Llama 都成立。）

**推论**：如果一段文本的"语义"在第 j 层（比如 j=12）就基本成形了，那我**只存第 j 层的隐藏态**就够——不用存原始 token，也不用存全部 36 层。之后需要用它时，从第 j 层继续往上跑就行。

这就是 QCMem 名字的由来：**Query-Conditioned Memory**，缓存的是"中层隐藏态"这种半成品记忆。

---

## 3. 方法本体（两个阶段）

把模型在**第 j 层切开**（split at depth j，默认 j=12，模型共 36 层）。

### WRITE（写入 / 建记忆）—— 只跑下半段
```
长文档 → 切成 512-token 的 chunk
每个 chunk:  过 layers[0 : j]  →  得到第 j 层隐藏态 h_j  →  存起来
```
- 每个 chunk 只跑了前 j 层（前 1/3），且只存**一层**的隐藏态 h_j。
- 存储量 ≈ 全部 KV 的 1/72（只存 1 层 hidden，不存 36 层 × K和V）。
- 每个 chunk 用**块内局部位置编码**（chunk-local RoPE），互相独立。

### READ（读取 / 回答）—— 只跑上半段
```
拿到问题 query:
  1. 用 bm25 检索, 从所有 chunk 里挑出最相关的 topk 个（比如 8 个）
  2. 拼成一个序列:  [sink token ; 选中的几个 chunk 的 h_j ; query 的 h_j]
  3. 给这个序列全新的位置编码, 过 layers[j : L]  →  得到答案的 logits
```
- **关键**：喂进上半段的序列长度是**固定的**（sink + topk×chunk + query ≈ 6657 token，chunk512/topk12 时），**跟原文有多长完全无关**。
- 原文 8k 也好、128k 也好，READ 阶段模型看到的永远是这 ~6.6k token。所以**永远不会超出模型的原生窗口**。

### 一个直觉图
```
        原文 (可以任意长, 比如 128k)
              │  切 512-chunk, 各过前 j 层
              ▼
    [h_j(1)] [h_j(2)] ... [h_j(N)]   ← 缓存的中层隐藏态 (存储 ~1/72 KV)
              │  bm25 按 query 检索 topk
              ▼
    [sink ; h_j(选中几块) ; h_j(query)]   ← 固定 ~6.6k, 与原文长度无关
              │  过后 (L-j) 层
              ▼
            答案
```

---

## 4. 一个关键旋钮：j

切分深度 j 是连续可调的，它把两个极端连起来：
- **j = 0**：什么都不缓存，READ 时从头跑全部层 = 就是标准 RAG（全上下文精确重算）。我们验证过 j=0 的输出和直接全喂模型**逐比特一致**（max logit diff < 1e-4）。
- **j = L（=36）**：全都缓存了，READ 时一层都不用跑 = closed-book（模型凭记忆瞎答）。
- **j = 12（我们用的）**：缓存前 1/3 的"理解成果"，重算后 2/3 的"生成"。省 2/3 算力 + 存储只要 1/72。

---

## 5. 训练（让它更好用）

零训练时 QCMem 也能跑，但 readout（从中层隐藏态生成答案）不够准。我们做了一个**自蒸馏**：
- **teacher** = j=0（全精确重算，质量最高）
- **student** = j=12 + 一个小 LoRA
- 让 student 学着从"只缓存到第 12 层"也能得到和 teacher 一样的输出。
- 数据是**纯 PG19 自然文本**（零合成 QA），4000 步。

这一步把 QCMem 从"能跑"提升到"精度追平全上下文"。

---

## 6. 和你可能熟悉的方法的关系

| 方法 | 缓存什么 | READ 长度 | 超窗口(128k) | 和 QCMem 的区别 |
|---|---|---|---|---|
| **full-context** | 不缓存，全喂 | O(原文) | ❌ 崩 | QCMem READ 长度恒定 |
| **RAG** | 原始文本片段 | O(检索片段) | 部分缓解 | QCMem 检索的是"半成品隐藏态"，且只重算上半段 |
| **KV-Direct**(2603.19664) | residual，重算全部层 KV | O(原文) | ❌ 崩 | QCMem 只重算上半段(layer-partial) + 检索固定长度 |
| **HCache**(2410.05004) | 中层 activation | O(原文) | ❌ 崩 | QCMem 有检索(固定长度) + 有训练 |
| **MemoryLLM** | 固定 memory bank | 固定 | 会 FIFO 丢失 | QCMem 检索不丢早期信息(bank 无溢出) |

**一句话定位**：QCMem 是"检索式 + layer-partial 重算"的组合。它最独特的地方 = **READ 长度恒定**（其它全上下文类方法都是 O(原文)），这让它在超出模型原生窗口的超长档上是**唯一还能工作的**。

---

## 7. 效果概览（详见 QCMEM_PAPER_DRAFT.md §2）

- **超长档是杀手锏**：128k 时 full-context / KV-Direct 全崩到 0（超模型窗口），QCMem RULER niah 仍 100、LongEval 0.98。
- **窗口内追平**：调好检索 topk 后，LongEval 32k=1.00 打平全上下文；RULER multikey 32k=100。
- **效率**：显存恒定 ~18GB（full 128k 要 89GB），prefill 快 7.6×。
- **诚实的短板**：需要精确定位单个事实、且信息全在窗口内时，全上下文方法可能略强；纯抽象文档 QA（LongBench）绝对分低（但那是任务难，所有方法都低）。

---

## 8. 术语速查

- **h_j**：第 j 层的残差流隐藏态（我们缓存的东西）
- **chunk**：512 token 的文本块（WRITE 的粒度）
- **topk**：READ 时 bm25 检索挑几个 chunk（每任务最优值不同，4-12）
- **sink**：序列开头的 anchor token（attention sink，稳定注意力）
- **resume_j / split depth**：切分层，= j
- **read_len**：READ 阶段喂进上半段的总 token 数（QCMem 恒定 ~6.6k）
