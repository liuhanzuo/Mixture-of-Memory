## 0. TL;DR

Fix Y did not fail because of a single mechanism. It failed because the code contains **two independent bugs that neutralise one another's supposed fix**, on top of a **fundamental architectural conflict** between VQ-EMA and InfoNCE. The evidence:

| Observation | Implication |
|---|---|
| `dead_revived=0` throughout Y2 (entire 2250+ fwd steps) | Revival mechanism is inert — **Bug #1** |
| Y2 top1_sim 0.644 → 0.043 → 0.003 (monotone collapse) | VQ-EMA drives keys toward query centroid |
| Y2 `pairwise_cos=0.55` stable but top1_sim at floor | Pair-cos is a red herring; real issue is **query collapse** |
| qa_loss stable at 5.0–5.8 in Y2 (vs log(512)=6.24) | InfoNCE gradient is computed, but its parameter updates are **overwritten** every step by VQ-EMA — **Bug #2** |

**Fix Z (recommended, confidence 72%)**: Remove VQ-EMA entirely + freeze `slot_keys` to random orthogonal init + rely on `load_balance_loss` to regularise `Q_sel`. This is the simplest architecture with the strongest literature backing (random hash routing, LSH, JL lemma) and eliminates all the failure modes observed across Fix V/X/Y.

If Fix Z passes fwd=500 with top1_sim > 0.010 but stalls before fwd=2000, **Fix Z.2 (chunk-pooled queries instead of single mean-pooled query)** is the next lever.

## 1. Bug #1 — Dead-Slot Revival is Dead-on-Arrival

### 1.1 The bug (selector.py L115–116, L255–269)

```python
# L115–116 — init
self.register_buffer('ema_cluster_count', torch.ones(num_slots))  # all slots start at 1.0

# L253–269 — update path
assigned = new_count > 0
if assigned.any():
    self.ema_cluster_count[assigned] = (
        alpha * self.ema_cluster_count[assigned]
        + (1.0 - alpha) * new_count[assigned]
    )
    # ... only writes slot_keys[assigned]
# Unassigned slots: NOTHING happens to ema_cluster_count
```

```python
# L275 — revival detection
dead = self.ema_cluster_count < dead_slot_reset_threshold  # threshold = 0.5
```

### 1.2 Why revival never fires

For any slot j:
- **Initialization**: `ema_cluster_count[j] = 1.0`
- **When j is selected (assigned=True)**: `count[j] ← 0.9·count[j] + 0.1·new_count[j] ≥ 0.9·count[j] + 0.1·1 ≥ 1.0` (if count was ≥ 1 and new_count ≥ 1).
  - Under DDP (8 GPUs × B=1) and uniform routing (B·top1/N = 8/512 = 0.015 expected assignments per slot), new_count[j] is 0 or 1 mostly.
  - Occupied slots: new_count ≥ 1, update drives count→1.0 steady state.
- **When j is NOT selected (assigned=False)**: `count[j]` is **NOT UPDATED AT ALL**. It stays at whatever it was before — which is initially 1.0.

**Result**: `ema_cluster_count` is bounded below by 1.0 for the entire lifetime of the run. The threshold 0.5 is mathematically unreachable. `dead_revived=0` exactly as the logs confirm.

### 1.3 The correct van den Oord 2017 semantics

```python
# ALL slots' counts decay every step (not just assigned)
self.ema_cluster_count = alpha * self.ema_cluster_count + (1.0 - alpha) * new_count
self.ema_cluster_sum   = alpha * self.ema_cluster_sum   + (1.0 - alpha) * new_sum
```

Under this, for unassigned slots: `count ← 0.9·count + 0 → 0.9·count → 0.81·count → ...`. After ~ln(0.5)/ln(0.9) ≈ 6.6 steps a slot that hasn't been hit crosses the 0.5 threshold and gets revived.

This is a **one-line fix**. But it is not sufficient in isolation — see §3.

## 2. Bug #2 — VQ-EMA Erases InfoNCE Gradients Every Step

This is the critical finding the user asked about.

### 2.1 The architecture

```python
# selector.py L269 (inside vq_ema_update, called INSIDE forward() when training)
self.slot_keys.data[assigned] = new_keys     # <<< HARD IN-PLACE WRITE
```

`slot_keys` is a `nn.Parameter` registered in the optimizer. In a normal training step:

1. **forward()**: compute logits using `self.slot_keys`. Inside forward, call `vq_ema_update()` → **overwrite `slot_keys.data[assigned]` with EMA mean of queries**.
2. **Compute losses**: LM loss + InfoNCE loss (qa_weight · `query_alignment_loss()`).
3. **backward()**: accumulate gradients into `slot_keys.grad` for BOTH paths (LM through STE, InfoNCE directly).
4. **optimizer.step()**: apply Adam update: `slot_keys ← slot_keys - lr · Adam(slot_keys.grad)`.
5. **Next forward()**: re-enter `vq_ema_update()` → **overwrite `slot_keys.data[assigned]` again, with fresh EMA mean**.

**The overwrite in step 5 completely erases the Adam update from step 4** for every slot that was assigned in the current step. The small amount of InfoNCE gradient that survives only touches **unassigned slots** — which, under uniform routing (N=512, top-1 picks 8 slots per DDP step out of 512), is 98.4% of the codebook. But for those unassigned slots, InfoNCE gradient magnitude is dominated by the negative-sample term `-T · (softmax_j) · q ≈ -10/512 · q ≈ 0.02·q` per step — **two orders of magnitude smaller** than the positive-sample term that would have flowed to the assigned (winning) slot.

### 2.2 Quantitative gradient budget

InfoNCE gradient magnitudes at random init (from rpt_20260430_0637):
- Positive slot (the winning k_pos): `|∂L/∂k_pos| ≈ T · (1 - 1/N) = 10 · 0.998 ≈ 9.98`
- Negative slot (any other k_neg): `|∂L/∂k_neg| ≈ T · (1/N) = 10/512 ≈ 0.0195`

Per step, with qa_weight=0.05:
- Effective positive gradient: `0.05 · 9.98 = 0.499` on the winning slot
- Effective negative gradient: `0.05 · 0.0195 = 0.00098` on each other slot

The winning slot's InfoNCE update → **erased** in the next step by VQ-EMA overwrite.
Each non-winning slot gets `0.00098` per step. Over 2000 steps: cumulative magnitude budget ≈ `sqrt(2000) · 0.00098 ≈ 0.044` (Adam normalises, so this is a per-parameter displacement budget in units of the initialized std=0.1 key scale ≈ 0.44 std-units).

**Result**: InfoNCE effectively never moves `slot_keys` meaningfully for assigned slots; for unassigned slots the signal is 500× weaker than for assigned. This is the **mathematical reason qa=0.05 fails**. It is NOT a "weight too small" problem — it is an **architectural opposition**: VQ-EMA and InfoNCE both write to `slot_keys`, but VQ-EMA writes last and hardest.

### 2.3 Does raising qa solve it?

**No.** Even at qa=1.0:
- Positive slot InfoNCE grad ≈ `1.0 · 9.98 = 9.98` per step → Adam normalises → effective step ≈ `lr/sqrt(v_avg) · direction ≈ 2e-4`.
- This Adam step of ~2e-4 is applied.
- Next forward: `slot_keys.data[winner] = normalize(ema_mean_of_queries)` — this is **~unit magnitude displacement** from the Adam-updated value back to the EMA-mean, erasing all InfoNCE progress every step.

Opposition is structural, not scalar. qa=100 would still fail.

## 3. Even if Both Bugs Fixed, VQ-EMA Cannot Succeed

### 3.1 The query-collapse root cause

`q = F.normalize(Q_sel(pool_of_H))` where `pool_of_H = mean(H, dim=1)`. Two observations:

1. **Mean-pooling destroys diversity**: For a batch of B=1 samples from PG-19, the mean of 4096 tokens yields a vector that is dominated by the *common mode* of the LM's hidden-state distribution (LayerNorm preserves the common mode). Across a DDP batch of 8, all 8 queries point in approximately the same direction — cosine similarity typically 0.85–0.95 between batch-item queries on a pretrained Llama.
2. **VQ-EMA averages over collapsed queries**: Each slot j's EMA mean `sum_of_winning_queries_j / count_j` → `E[q | j is winner]`. With highly similar queries across the batch, this expectation is ≈ `E[q]` regardless of j — the **global query centroid**.

Consequence: all "popular" slots' keys converge to the same direction → pairwise_cos rises → routing becomes uniform → top1_sim collapses.

### 3.2 Why Arm C's InfoNCE "delayed" collapse

From Y1/Y2/Y3:
- Y1 (no InfoNCE, norm_cap=5): killed fwd=700 at top1=0.0050
- Y2 (qa=0.05, norm_cap=5): stable 0.003 plateau for 2000+ steps — **at floor, not below**
- Y3 (no InfoNCE, norm_cap=10): collapse fwd=400 at top1=0.0034

Y2 didn't "succeed"; it plateaued at the **uniform-routing floor** (1/512 = 0.00195, so 0.003 is 1.5× floor — still "random"). InfoNCE on unassigned slots provided weak repulsion sufficient to keep `pairwise_cos` at 0.55 (vs Y3's 0.85) — but not sufficient to establish differentiated addressing.

### 3.3 Implication

Even if we:
- Fix Bug #1 (revival triggers on decay for all)
- Remove Bug #2 (decouple slot_keys from EMA overwrite)
- Do both at once

…the underlying query-collapse problem (§3.1) means **any mechanism that derives keys from queries will produce collapsed keys**. This is a no-go for VQ, online k-means, repulsive EMA, and any EMA-of-queries variant.

## 5. Recommended Fix Z

### 5.1 Fix Z.1 (Primary, P≈70%) — Frozen Random Slot Keys

**Motivation**: If the real bottleneck is query diversity (§3.1), slot_keys don't need to learn anything — they just need to be diverse. Random Gaussians in d=128 satisfy this by Johnson-Lindenstrauss: N=512 random unit vectors in R^128 have expected pairwise cosine 0 with std 1/sqrt(128) ≈ 0.088. Two random keys have <0.3 cosine similarity with >99% probability.

**Implementation** (4 file changes):

```python
# selector.py __init__
# REPLACE nn.Parameter(...).requires_grad = True
# WITH:
self.slot_keys = nn.Parameter(
    F.normalize(torch.randn(num_slots, selector_dim), dim=-1),
    requires_grad=False,  # <<< FROZEN
)

# DELETE: ema_cluster_sum, ema_cluster_count buffers
# DELETE: vq_ema_update() method
# DELETE: query_alignment_loss() method
# DELETE: forward()'s call to self.vq_ema_update(...)
# DELETE: forward()'s self.last_q = q, self.last_idx = idx

# config.py
# DELETE: ema_update_weight, ema_update_alpha, dead_slot_reset_threshold,
#         query_alignment_weight, slot_value_norm_cap (or keep at 0 default)

# layer.py
# DELETE: query_alignment aux-loss block
# DELETE: dead_slots, dead_revived from QUERY_DIAG logging
# KEEP: load_balance_loss (this is the ONLY regularizer on Q_sel now)

# Training script — no new CLI flags; remove --query_alignment_weight, --ema_*, etc.
```

### 5.2 Why this has higher P(success) than what we tried

1. **No EMA overwrite** → LM gradient through STE flows cleanly to `Q_sel` without being erased.
2. **No opposing objectives on slot_keys** — they don't train at all.
3. **Q_sel is the sole learnable component** for routing. Its job: map `pool_of_H` to query-space so that the N=512 random directions correspond to N=512 "concepts" Q_sel learns to extract.
4. **Load-balance loss** (switch-transformer style) pushes Q_sel to spread its outputs across all 512 random directions → anti-collapse pressure on Q_sel rather than on keys.
5. **Precedent**: 
   - Random hash routing (Roller et al., "Hash Layers for Large Sparse Models", NeurIPS 2021, arXiv:2106.04426) shows fixed-hash-routed MoE is competitive with learned routers on LM.
   - Johnson-Lindenstrauss: random orthogonalish projections preserve pairwise structure with high probability.
   - LSH nearest neighbor: fixed random hyperplanes suffice for billions of items.
6. **Testable in <500 steps**: No warmup dynamics. If Q_sel can learn, it can show top1_sim > 0.010 within 200 steps. If it can't, the bottleneck is Q_sel (→ Fix Z.2), not keys.

### 5.3 Kill criteria for Z.1 test

- fwd=200: top1_sim > 0.005 AND pairwise_cos < 0.20 (keys stay diverse — they must, they're frozen)
- fwd=500: top1_sim > 0.010 (baseline success)
- fwd=1000: top1_sim > 0.020 (healthy)

If fwd=500 shows top1_sim < 0.005, Q_sel cannot differentiate — move to Z.2.

### 5.4 Fix Z.2 (Secondary, P≈75%) — Chunk-Pooled Queries

If frozen random keys alone don't solve it, the next surgery is query-side:

```python
# Instead of single pool_of_H = H.mean(dim=1) → [B, d]
# Pool over K=16 temporal chunks of size T/16:
B, T, d = H.shape
K = 16
chunk_size = T // K
H_chunks = H[:, :K*chunk_size, :].reshape(B, K, chunk_size, d)
pool_of_H_chunks = H_chunks.mean(dim=2)            # [B, K, d]
q = F.normalize(Q_sel(pool_of_H_chunks), dim=-1)   # [B, K, d_sel]
# Route each chunk separately to top-k slots
logits = torch.einsum("bks,ns->bkn", q, slot_keys) * T_sel  # [B, K, N]
# Then aggregate per-chunk routing decisions per batch item
scores_per_sample = logits.mean(dim=1)                        # [B, N]
# Top-k over aggregated scores
_, idx = torch.topk(scores_per_sample, k=top_k, dim=-1, largest=True, sorted=False)
```

**Effect**: K=16 queries per batch item, capturing temporal variation within the sequence. The query distribution now has K× more diversity → routing signal is K× richer → `Q_sel` gradient has K× more samples per step.

Requires changes in layer.py forward(); ~80 lines. Can be added later as a sequential Z.2 test if Z.1 doesn't clear fwd=500.

### 5.5 Fix Z.3 (Fallback, only if Z.1 and Z.2 both fail)

If none of the above works, pivot to **attention-based memory** (ARMT / Memformer style): discard the "slot selector" concept entirely. Replace with full cross-attention memory:
- Memory = [B, N, d_slot]
- Cross-attention: content_tokens attend to ALL N memory slots (no top-k)
- Writeback: gated EMA on memory from content
- Cost: O(T·N·d) per layer instead of O(T·k·d), but N=64–128 is manageable.

This matches the "Attention Matching" direction already flagged in CLAUDE.md as Priority 0 post-2026-04-23-pivot. The slot-routing investigation (Fix C…Z) has consumed 4 days with 0 successful results; it may be time to fold it and pursue the priority track.

## 6. Triangulation

### 🟢 Proposer (best case for Fix Z.1)

Frozen random slot_keys work immediately:
- First 50 steps: LM gradient through STE trains Q_sel; Q_sel learns to distribute hidden states across the 512 random directions.
- By fwd=200: Load-balance loss has equalised slot usage. Top1_sim > 0.010 achieved because Q_sel is now mapping similar hidden states to similar query directions, and those map deterministically to nearby slots via the fixed random key geometry.
- Key diagnostic: `pairwise_cos` STAYS LOW (< 0.15) because keys are frozen. If we see pairwise_cos stay at ~0.08 (init value) AND top1_sim rising, that's the success signal.
- Precedent: Roller et al. 2021 show hash-based MoE routing matches learned routers at Switch-Transformer scale.

### 🔴 Skeptic (biggest risk to Fix Z.1)

**The real bottleneck is Q_sel, not slot_keys.** If `Q_sel(pool_of_H)` produces near-identical outputs across the batch (query collapse) regardless of what slot_keys look like, then ANY routing mechanism fails — including frozen random. Evidence:
- In Fix X.2, the report stated "qa_loss at log(512) means slot_keys receiving gradients but no differentiation signal." This suggests that even with unrestricted key training, the gradient into `Q_sel` was too weak/collapsed to produce diverse queries.
- Mean-pooling over T=4096 tokens destroys all intra-sequence variance. Q_sel input may genuinely be near-identical across batch items.

**Mitigation**: Fix Z.2 addresses this directly. The test protocol is: run Z.1 for 500 steps; if top1_sim stuck at ~0.002 (floor), pivot to Z.2.

### 🔵 Critic (blind spots)

1. **Load-balance loss might not be enough pressure on Q_sel.** If Q_sel is trained primarily by LM gradient (through STE), and LB loss has small weight (0.01), LB may not provide sufficient anti-collapse pressure. Consider raising LB weight to 0.1 as part of Z.1, OR combining with `entropy_aux_weight` (though Fix V/W said harmful — but that was in context of trainable keys where entropy pushes keys to collapse; with frozen keys, entropy on scores pushes Q_sel to spread, which is the right direction).
2. **We have not directly measured query diversity.** All our diagnostics (top1_sim, pairwise_cos, qa_loss) are proxies. A direct diagnostic would be: cosine similarity between `q` vectors across batch items and across time within a batch. This should be added to QUERY_DIAG in Z.1.
3. **Backward compat with pre-Fix-B checkpoints**: `slot_keys` was made a nn.Parameter in Fix B; freezing it doesn't break state_dict loading but we should confirm optimizer doesn't choke on `requires_grad=False` params in its param_groups (standard PyTorch: it doesn't include them).
4. **The user is 4 days into slot-routing bug chasing.** Even if Fix Z.1 works, ask: is slot-based routing ever going to beat attention-matching or 4-bit KV quant? CLAUDE.md says those are priority 0. At some point the investment into this architecture may not pay off vs pivoting.
