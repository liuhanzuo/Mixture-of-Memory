## 2. Root Cause: Hardcoded temperature=10.0

**THE BUG**: In `src/memory/mem_space/selector.py` lines 152–154:

```python
temperature = 10.0
logits = torch.einsum("bs,bns->bn", q, k) * temperature  # cosine sim × temperature, [B, N]
scores = F.softmax(logits, dim=-1)                # [B, N]
```

`temperature` is a **hardcoded local Python variable**, NOT a configurable hyperparameter and NOT in `MemorySpaceConfig`. There is no CLI flag for it.

### 2.1 Why temperature=10 destroys Fix N

The training gradient to `slot_keys` has two competing sources:

**Path A: LM loss through STE proxy (layer.py lines 511–521)**

```python
# STE proxy (Fix J-A): slots NOT detached here
M_sel_slot_soft = torch.einsum("bn,bnd->bd", scores, slots)  # [B, slot_dim]
M_sel_hidden_soft = self.slot_to_hidden(M_sel_slot_soft.unsqueeze(1).expand(-1, cfg.top_k, -1))
M_sel_hidden = M_sel_hidden_hard.detach() + (M_sel_hidden_soft - M_sel_hidden_soft.detach())
```

Gradient flows: `lm_loss → M_sel_hidden → M_sel_hidden_soft → scores → logits = cosine_sim * T → slot_keys`

The gradient through softmax is: `d_loss/d_logits = scores * (d_loss/d_scores - sum_j(scores_j * d_loss/d_scores_j))`

The Jacobian of `logits = cosine_sim * T` with respect to `cosine_sim` is just `T`. Therefore:
```
d_loss/d_slot_keys ∝ T × (STE_gradient_through_cosine_sim)
```

**At T=10**: LM loss gradient to slot_keys is **10× larger** than at T=1.

**Path B: SKRL (selector.py slot_key_diversity_loss)**

```python
nk = F.normalize(self.slot_keys, dim=-1)  # [N, S]
cos_sim_pairs = (nk[i] * nk[j]).sum(-1)   # pairwise cosine
return cos_sim_pairs.mean()               # minimize → push keys apart
```

SKRL gradient: `d_skrl/d_slot_keys` — acts on `F.normalize(slot_keys)` directly. This gradient path does **NOT pass through temperature at all**. It is completely independent of T.

### 2.2 Gradient balance calculation

For a single training step, the update to `slot_keys`:
```
Δ(slot_keys) = -lr × (T × ∇_LM + skrl_weight × ∇_SKRL)
```

With T=10, lr=1e-3:
- LM gradient contribution: `1e-3 × 10 × ∇_LM = 1e-2 × ∇_LM`
- SKRL contribution at weight=0.10: `1e-3 × 0.10 × ∇_SKRL = 1e-4 × ∇_SKRL`

**Gradient ratio LM:SKRL ≈ 100:1** at skrl_weight=0.10, T=10.

At T=1 with the same skrl_weight=0.10:
- LM gradient contribution: `1e-3 × 1 × ∇_LM = 1e-3 × ∇_LM`
- SKRL contribution: `1e-4 × ∇_SKRL`

**Gradient ratio LM:SKRL ≈ 10:1** at T=1 — still LM-dominated but 10× more manageable.

### 2.3 Why this causes oscillation, not convergence

The LM loss gradient to `slot_keys` is NOT uniform-routing pressure in the same way as load_balance. It pushes each slot_key toward "best average query direction for the LM loss". With T=10:

1. A slot key gets pushed hard toward a "useful" query direction by LM gradient
2. SKRL slightly repels it away from neighbors (weak: ratio 100:1)
3. Another slot key's LM gradient pushes it toward a similar direction (all keys fight over the same "useful" queries)
4. The net effect: keys oscillate in a small neighborhood of the "average LM-useful direction"

This is NOT routing collapse (all identical) — it's "routing micro-clustering" where all keys chase the same few query types. mean_pairwise_cos ≈ 0 (random-like) because the keys are spread out in high-dimensional space, but they're not converging to the ≈ −0.002 equidistant-on-hypersphere configuration.

**The critical observation**: Even skrl_weight=0.10 cannot overcome T=10 × LM gradient because the LM gradient is 100× stronger and points in "collapse" directions (not random, not repulsive).

## 3. Secondary Contributing Factors

### 3.1 entropy_aux_loss (weight=0.001) pushes toward uniform routing

`entropy_aux_loss` returns `-entropy` (to minimize). Minimization = maximize entropy = push routing distribution toward uniform. This fights against the slot specialization that top1_sim divergence requires. However, at weight=0.001 this is a minor contributor compared to the LM-gradient / SKRL competition.

### 3.2 load_balance_loss (weight=0.001) also fights specialization

Fix N reduced load_balance from 0.01 → 0.001 (10×). But this only reduces one uniform-routing pressure; the dominant one (T=10 LM gradient collapse) remains.

### 3.3 SKRL gradient magnitude at the RANDOM (not collapsed) initial state

The Fix G / Fix N hypothesis assumed SKRL would work by "pushing keys apart". SKRL gradient is strongest when keys are IDENTICAL (O(1) = 2.0). But after 20+ steps of LM training with T=10, slot_keys are NOT all identical — they've already been pushed to random-looking positions by the LM gradient diversity. SKRL gradient at a random arrangement:
- Expected `E[cos_sim(key_i, key_j)]` ≈ 0 (random unit vectors in 128D)
- SKRL gradient ≈ mean of random unit vectors ≈ 0 (cancellation)

So SKRL is actually most effective before step 1 (pure initialization) and weakest in the "random oscillation" regime that T=10 creates. This is a **catch-22**:
- T=10 LM gradient moves keys away from pure symmetric collapse quickly (within 20 steps)  
- But moves them into "pseudo-random with LM bias" regime where SKRL has weak gradient
- SKRL needs keys to be near-collapsed to have strong gradient, but T=10 ensures they never stay collapsed long enough for SKRL to build momentum

## 4. Fix O Specification

### Primary Fix: Reduce temperature 10→1 (code change, 1 line)

**File**: `src/memory/mem_space/selector.py`, line 152  
**Change**: `temperature = 10.0` → `temperature = 1.0`

This is the ONLY way to fix the gradient imbalance — temperature is not in config, not a CLI flag, and cannot be changed without code modification.

**Expected result at T=1**:
- LM gradient to slot_keys: 1× (instead of 10×)
- SKRL gradient ratio improves from 100:1 to 10:1 at skrl_weight=0.10
- SKRL at weight=0.10 should now be sufficient to drive mean_pairwise_cos negative
- At T=1 the STE proxy still flows gradient (softmax is still differentiable), but it no longer overwhelms SKRL

**Risk analysis**:
- Reducing T from 10→1 makes the softmax less "peaky" (scores more uniform), which slightly reduces signal-to-noise in slot selection
- However, T=10 was never validated to be optimal — it was added at some point to "sharpen" selection but is now preventing the routing diversity needed for slot specialization
- The STE proxy gradient is still O(1/N) per slot (softmax derivative), just 10× weaker in absolute terms
- All other gradients (load_balance, entropy, LM through bypass path) are unaffected

### Make temperature a configurable parameter (recommended alongside primary fix)

Add to `MemorySpaceConfig`:
```python
selector_temperature: float = 1.0  # softmax temperature for slot selection
```

Add to `train_mem_space_pg19.py` argparse:
```python
parser.add_argument("--selector_temperature", type=float, default=1.0)
```

This allows future ablation without code changes.

### Secondary Fix (optional, run alongside): entropy_aux_weight 0.001→0.0

The entropy aux loss pushes toward uniform routing (fights slot specialization). With T=1 + SKRL=0.10, uniform-routing pressure should be zero. Set `--entropy_aux_weight 0.0` in Fix O ablation.

## 7. Revision of Fix N Assessment

Fix N was not a failure of the SKRL mechanism — it was a failure to account for the T=10 amplifier on the competing LM gradient. The diagnostic evidence (mean_pairwise_cos oscillating near 0, not stuck at +0.002 collapsed value) confirms:

- Keys ARE being repelled by SKRL (otherwise they'd collapse to +0.002 as in the pre-Fix-N baseline)
- Keys are NOT converging to −0.002 (SKRL is weaker than LM pull)
- The oscillation bandwidth [−0.003, +0.003] is exactly what gradient balance of ratio 100:1 predicts (SKRL creates 1% perturbations in a LM-dominated optimization landscape)

This is a **well-diagnosed, well-specified fix** — Fix O is a 1-line change with high confidence of resolving the oscillation.
