**下采样日志（watcher / tqdm / 每 N 步一行的 log）只能判「是否在推进」，不能用来算速率。速率只能用与信号同粒度的源 —— ckpt mtime。**

**Why:** 2026-08-17 我在**同一天、相隔 15 分钟**把 `.73` keep12 的 s/step 报错**两次，方向相反**：

| 数值 | 来源 | 我当时的说法 |
|---|---|---|
| 8.333 | watcher，5 个区间的**均值** | 「慢 5.2%，ETA 21:05」 |
| 7.500 | watcher，**众数**区间（40 步/300 s，4/4 全等） | 「**纠正**：快 5.3%，ETA 19:33」 |
| **7.9167–7.9215** | **ckpt mtime**，连续 5 个区间（500/2500/5000 步） | ✅ 真值，**1.0004× 基线，从未异常** |

**根因是 aliasing，不是「量化误差」那么轻。** watcher 每 **300 s** 采一次，trainer 每 **20 步**才写一行 log。
真速率 7.919 s/step ⇒ 300 s = **37.9 步** ⇒ watcher 只能看到 `40, 40, 20, 40, 40 …` 交替。于是：

- **取众数（40 步/300 s）系统性高估速度** → 7.50；
- **窗口端点落在交替两侧则系统性低估** → 8.33；
- **两个统计量都不会收敛到真值**，因为采样器比信号粗。加长窗口也不行（偏差不是噪声）。

**最痛的一点：第二次错发生在我以为自己在纠正第一次的时候。** 我把统计量从「均值」换成了「众数」，
**但没换数据源**。`7.50 = 4/4 完全相等` 看起来像铁证 —— 一致性只说明采样器稳定，不说明它准。

**How to apply:**
- **算速率只用 ckpt mtime**（`save_every` 已知 ⇒ Δstep 精确，Δt 由文件系统给）。至少取 3 个连续区间。
  watcher / tqdm / `grep 'step N'` 只回答「有没有在动」。
- **偏离基线 >2% 时，先问两个问题再下判断**：(1) 这个数是**哪个源**给的？(2) 那个源的**粒度**是多少？
  若 `采样周期 / 真速率` 不是 log 写入粒度的整数倍 → 必然 aliasing，该源的任何统计量都不可用。
- **「N/N 个区间完全相等」不是准确性的证据，是量化的指纹。** 真实的连续测量会有小抖动
  （对比：`.212` 的 2.4501/2.4510/2.4508、`.82` 的 5.8580–5.8648 —— 这种**参差**才是真测量的样子）。
- **换统计量 ≠ 换方法。** 发现一个数不可信时，第一反应应该是**换源**，不是在同一份坏数据上换算法。
- 若必须用 watcher 判速率（例如 ckpt 还没落地），**明确写「下界/上界，来源 watcher，粒度 20 步」**，
  不要写成一个点估计。
- 同族：[[one-sample-is-not-a-trend-or-state]]、[[tqdm-elapsed-and-counter-have-different-origins]]、
  [[ckpt-interval-rate-is-not-compute-rate]]（那条讲 ckpt-flush 会让 amortised 高估 ~13%，
  与本条互补：**ckpt mtime 是最好的源，但要说清 compute 还是 amortised**）。
  四条共同点：**我拿一个便利的读数当成了被测量本身。**
